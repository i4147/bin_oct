## What "already has a module docstring" means
A file has a module docstring iff `ast.get_docstring(ast.parse(source))` returns a
non-None, non-empty string. Use exactly this check to decide SKIP vs. CHANGE.
- A triple-quoted string as the first statement → SKIP.
- A string literal that is not the first statement → not a docstring → ADD one.
- An f-string as the first statement (JoinedStr, not Constant) → not a docstring by
  Python's rules; mark SKIPPED-NEEDS-REVIEW and do not touch (don't create a second
  "first-string" and change semantics).
- Empty or whitespace-only `__doc__` → treat as missing and ADD one.

## Where the docstring goes
- Line 1 if the file has no shebang / encoding comment.
- After the shebang line (`#!...`) and after any PEP 263 encoding line
  (`# -*- coding: ... -*-`), whichever comes later.
- BEFORE any `from __future__ import ...` line, before any import, before any other
  statement.
- Use triple double quotes: `"""..."""`.
- If the docstring is a single line, keep `"""text"""` on one line. If multi-line,
  open on the line after the opener is conventional: use
  `"""\nSummary line.\n\nMore detail.\n"""` OR a single-line summary if that's all
  that's needed. Do not invent sections.

## What the docstring should say (quality bar)
The docstring MUST be accurate to the file's actual contents. Do not hallucinate.

Process per file:
1. Read the whole file.
2. Identify: what this module provides (CLI entry point? library helpers? a single
   class? a single function? constants?), the top-level public names it defines, and
   any side effects at import time.
3. Write a one-line summary in imperative mood ("Parse X…", "Provide helpers for
   …", "Define the Foo class…"). Keep it under ~88 characters.
4. If and only if the file has clearly non-obvious behavior (side effects, complex
   setup, external file/config dependencies, a CLI it exposes), add a short second
   paragraph — 1–3 sentences max — describing that. Otherwise stop at the summary.
5. Do not list every function. Do not add "Usage:", "Examples:", "Args:" or similar
   sections. Do not mention implementation details (line counts, "this module
   imports…"). Do not mention "This module" as filler — describe the thing directly.

Examples of the right shape:
- `"""Load, validate, and summarise the project configuration file."""`
- `"""Command-line entry point for the ingest pipeline."""`
- `"""Data models shared by the scheduler and worker processes."""`

If after reading the file you genuinely cannot determine what it does, mark
`SKIPPED-NEEDS-REVIEW` with the reason — do not fabricate.

## Blockers (→ mark SKIPPED-NEEDS-REVIEW, continue)
- File has a syntax error.
- File is generated (auto-generated / "do not edit" / "generated by" markers).
- File has a top-level `__doc__` assignment before any other statement (docstring
  insertion would either shadow or be shadowed — needs human review).
- File is a very thin wrapper whose only content is `from x import *` and you cannot
  determine a meaningful summary beyond restating the import.
- File has an f-string as its first statement (see "What already has a module
  docstring means" above).
- Insertion would require changing any other line of the file.
